1 Multi-tenant isolation — one SQLite file per tenant

Data is isolated per user → per store → per project (audit) → per Audit Cadence, each as its own physical SQLite file. Campaign IDs from different Amazon accounts can never collide because the files are physically separate. A bulk uploaded under one cadence only ever drives that cadence. The get_db FastAPI dependency folds ?store=&project=&audit_type= into the db path, so every router is auto-scoped with zero per-router code.

2 PPC Audit star schema (pipeline db)

Dimensions hold structure (slow-changing); one fact_performance table holds raw metrics stamped with snapshot_date (every upload = a snapshot → enables trends). View is ASIN-rooted at query time (build_tree re-roots campaign→ad-group→ad by the ad's ASIN). Solid lines = real FK (ON DELETE CASCADE); dashed = polymorphic link (fact_performance.entity_type/entity_id, no DB FK). Derived rates (ACoS/CTR/CVR/ROAS) are never stored — computed in metrics.py.

3 Side tables & isolated feature tables (same pipeline db)

These live in the same per-cadence db but are deliberately separate from the star schema — each runs off its own dedicated upload and never shifts the audit's "latest snapshot". The five cadence panels and the Product Ads tab each keep their own table. Only cadence_run → cadence_task has a real FK; the rest are independent (keyed by ASIN / campaign_id / date / search term).

4 Central authentication db (separate engine)

backend/data/auth.db — its own engine + Base, fully separate from the per-store/project pipeline DBs. Stdlib PBKDF2 password hashing (no native dep). Login mints an opaque bearer token with a sliding 12h expiry; one active session per user (a new login revokes prior sessions). Superuser SAdmin seeded on startup. Every data router is gated behind Depends(auth.current_user).
